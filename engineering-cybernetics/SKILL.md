# 工程控制论 Agent 指导框架

基于钱学森《工程控制论》21章的系统化提炼，将控制论的核心思想映射为 Agent 架构设计和任务执行的可操作原则。

## 触发条件

当任务涉及以下任一特征时，加载本 skill：
- 多步骤、多依赖的复杂推理
- 多 Agent / 多工具并行协作
- 系统架构设计
- 错误恢复和容错需求
- 需要自适应调整策略
- 大规模信息聚合
- 不可逆的高风险操作

---

## 15 条核心设计原则

### P1 · 稳定性优先 (Stability First)
> 确保 Agent 在各类输入扰动下输出不发散。稳定性是所有质量指标的前提。

- ✅ 对关键决策点设置一致性检查：当前推理是否与之前一致？
- ❌ 不要片面追求单次精度而牺牲推理链稳定性

### P2 · 反馈闭环设计 (Feedback Closed-Loop)
> 任何关键决策链必须包含验证反馈环：生成→验证→修正→再生成。

- ✅ 为关键输出建立生成-验证-修正循环，设最大迭代次数
- ❌ 不要仅在最终输出处验证——中间节点也应设验证点

### P3 · 状态可观测原则 (State Observability)
> Agent 的内部推理状态必须可观测——通过日志/中间输出完整重构推理过程。

- ✅ 定期输出可观测的中间状态（推理摘要、关键变量值、置信度）
- ❌ 不要在外部不可见的情况下做关键决策

### P4 · 能控性边界界定 (Controllability Boundary)
> 明确 Agent 的可控维度（可通过指令调优）和不可控维度（模型固有局限）。

- ✅ 设计前做能控性评估：工具集是否覆盖所有必要操作类型？
- ❌ 不要对不可控维度浪费优化资源

### P5 · 有限时间收敛 (Finite-Time Convergence)
> 在给定推理预算内不偏离正确方向超过允许范围，设定明确终止条件。

- ✅ 为每个任务设定最大步数/token/时间预算，到上限输出当前最佳
- ❌ 不要为追求完美渐近收敛而无限迭代

### P6 · 多指标帕累托权衡 (Multi-Objective Pareto Trade-off)
> 准确率/延迟/成本/安全性之间存在帕累托前沿，必须按场景确定优先级。

- ✅ 部署前明确场景的指标优先级，据此选择模型规模和参数
- ❌ 不要宣称某个 Agent 在所有维度上"最好"

### P7 · 模块化串联设计 (Modular Series Design)
> 将复杂 Agent 分解为可独立开发的模块（检索→推理→工具→验证）。

- ✅ 为每个模块定义清晰的输入输出契约，独立评估性能
- ❌ 不要将检索、推理、验证逻辑混杂在同一个 prompt 中

### P8 · 协调优先于独立最优 (Coordination over Independence)
> 多 Agent 协作时，全局协调约束优先于局部最优；有选择地保留有益耦合。

- ✅ 先独立优化各 Agent 单体（两步设计法第一步），再设计协调机制（第二步）
- ❌ 不要片面追求完全解耦——某些自然耦合（信息传递）若强行消除反而降低效率

### P9 · 冗余容错与多路径验证 (Redundancy Verification)
> 关键决策不依赖单次执行——采用多路径独立推理+投票/融合的冗余策略。

- ✅ 关键决策点实施至少 2/3 表决冗余；每个工具配备至少一个 fallback
- ❌ 不要在不可逆操作上依赖单次推理结果；也不要简单重复同一操作作为重试

### P10 · Kalman 式递推状态估计 (Kalman-Style State Estimation)
> 每次工具调用后像卡尔曼滤波一样更新状态：预测→观测→计算残差→更新估计。

- ✅ 维护任务进展的信念状态；对不一致的工具输出做加权融合
- ❌ 不要对所有工具输出赋予相同信任度——应根据可靠性动态调整增益

### P11 · 自适应与模型参考 (Model-Reference Adaptation)
> 以理想行为为参考模型，偏差 e(t) 驱动策略调整；常规任务用固定策略，异常任务切换探索模式。

- ✅ 为常见任务类型预设最优策略模板；检测异常时自动切换到安全加固策略
- ❌ 不要对所有任务用同一套策略；也不要在无必要时频繁切换

### P12 · 信息效率与信道容量 (Information Efficiency)
> 上下文窗口有信息承载上限 C = F·log₂(1+P/N)。每步推理应追求最大信息增益。

- ✅ 评估每步推理的信息增益；长对话中压缩冗余信息，保留高密度内容
- ❌ 不要在上下文窗口中填充大量低信息量内容

### P13 · 有限状态机完备性 (FSM Completeness)
> Agent 核心控制流应形式化为有限状态机（状态集, 输入集, 输出集, 转移函数, 输出函数）。

- ✅ 穷举所有 (当前状态 × 输入类型) 组合，确保每个组合有预定义行为
- ❌ 不要留下"未定义"的 (状态, 输入) 组合——会导致不可预测行为

### P14 · 摄动控制与 Min-Max 鲁棒 (Min-Max Robustness)
> 小偏差沿推理链传播放大，必须早设检查点并尽早修正；针对最坏情况预设降级方案。

- ✅ 在长推理链中设检查点评估累积偏差；从最终目标反向推导关键步骤权重
- ❌ 不要在偏差已累积到不可修复时才启动修正

### P15 · 工程近似与复杂度适配 (Complexity Matching)
> 简单任务用简化模型快速响应，仅当复杂度超出阈值时才启用完整推理链。

- ✅ 对每个任务做复杂度评估，根据复杂度选择匹配的处理层级
- ❌ 不要对所有任务一刀切地使用完整推理链

## 按任务类型匹配

| 任务类型 | 适用原则 | 执行要点 |
|---------|---------|---------|
| **简单事实查询** | P15, P1, P7 | 简化模型快速响应，低温度确保确定性 |
| **复杂推理** | P2, P5, P7, P9, P14 | 反馈闭环+多路径验证+检查点+Kalman 式状态跟踪 |
| **多工具并行** | P8, P13, P9 | 确保子任务独立性，FSM 管理并行状态，结果不一致用融合 |
| **多 Agent 协作** | P8, P13, P7 | 两步设计法：先独立优化各 Agent，再设计 Orchestrator 协调 |
| **代码生成执行** | P2, P5, P9, P10 | 生成→执行→检查→修正闭环，预测-更新定位 bug |
| **高风险操作** | P9, P1, P14, P6 | 最高级三路验证+人工确认，安全性优先级最高 |
| **长时间对话** | P12, P3, P10, P15 | 管理信道容量，压缩冗余，递推更新意图估计 |
| **对抗输入** | P1, P14, P6, P11 | 稳定性优先，Min-Max 最坏防御，检测异常切换安全策略 |
| **在线学习调优** | P11, P4, P5 | MRAC 模型参考自适应，步进探测 Δx→Δy→调整，设探索预算 |
| **信息聚合综合** | P12, P9, P3 | 评估每源信息密度，多源交叉验证，分层汇聚压缩 |

## 执行检查清单

Agent 面对复杂任务时，按此清单逐项检查：

- [ ] **建模**：是否建立了清晰的任务状态模型？（P1, P3）
- [ ] **能控**：是否明确了可控维度与不可控维度？（P4）
- [ ] **反馈**：是否有验证闭环？（P2）
- [ ] **预算**：是否设定了最大步数/时间/token 限制？（P5）
- [ ] **优先级**：多目标冲突时优先级是否明确？（P6）
- [ ] **模块化**：是否可分解为独立子任务？（P7）
- [ ] **协调**：多 Agent/工具间的依赖和冲突是否已处理？（P8）
- [ ] **冗余**：关键决策是否有备份验证路径？（P9）
- [ ] **状态**：是否维护了任务进展的递推状态估计？（P10）
- [ ] **自适应**：是否有异常检测和策略切换机制？（P11）
- [ ] **信息**：每步推理是否产生实质性信息增益？（P12）
- [ ] **完备**：所有 (状态×输入) 组合是否有预定义行为？（P13）
- [ ] **鲁棒**：是否针对最坏情况预设了降级方案？（P14）
- [ ] **适配**：任务复杂度是否匹配处理层级？（P15）

## 反模式（不要做的事）

- ❌ 跳过建模直接执行 → 对应控制论中"未分析即设计"
- ❌ 忽略反馈信号 → 开环控制必然偏离
- ❌ 单点故障无备份 → 违反冗余容错原则
- ❌ 无限迭代不设预算 → t→∞ 的渐近完美在工程中无意义
- ❌ 对所有任务一刀切 → 简单问题浪费资源，复杂问题不够深入
- ❌ 陷入重复循环 → 监控并打破极限环（尝试→失败→重试同一方法）
- ❌ 信任度均等 → 不同工具有不同可靠性，应像卡尔曼增益自适应调节
